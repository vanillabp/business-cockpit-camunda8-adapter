## The cockpit learns of a suspension by asking the cluster, once an hour by default

Proposed by story 1544. No number yet. Whoever merges it gives it the next free one and corrects
the places listed at the end.

**Why.** A cluster of the 8.10 line can suspend a process instance, over REST and in Operate. It
tells no client about it: no listener runs, and no job is created. A resumption is just as silent.
The search shows both. The instance gets the state `SUSPENDED` and a `suspendedDate`, and both go
away on the resumption. The cockpit shows a suspension only where a BPMS half reports it, and since
the cockpit's decision of 2026-11-02 only the reports of a suspension and an activation change that
state. A later change or end no longer heals a missed activation. So this extension has to find
both, and it has to ask.

**What holds.**

- Once per interval, one search per adapter id and tenant: every instance in state `SUSPENDED` of
  the processes this extension wired, page by page. The interval is
  `vanillabp.adapters.<id>.cockpit.suspension-check-interval`, one hour by default. `0` switches the
  check off. It is the first configuration key of this extension, and it stands at the adapter id,
  because the check runs once per cluster. The section `vanillabp.cockpit` belongs to the cockpit's
  `extensions-commons`, which refuses a key it does not know there.
- The result is compared with the set of the run before. A new instance was suspended. Its
  `suspendedDate` is the moment reported, so every node reports the same moment. An instance which
  left the set was resumed or has ended. One search by their keys (`processInstanceKey in [...]`)
  says which. An ended instance gets no report.
- Only where something changed, three more searches follow, each for all changed instances at
  once: the open user tasks of exactly those instances, the variable with the workflow aggregate's
  id, and the audit log. A run without a change is one search.
- Only the instance which is suspended itself is reported. A called instance is not suspended with
  its caller, so its tasks are not reported. A suspended instance which is a case of its own is
  reported as a workflow as well, and a suspended step of another case is not (decision 3).
- The person is the `actorId` of the youngest `SUSPEND` or `RESUME` entry of the audit log with
  the result `SUCCESS`. It goes out as the initiator of the report, which the cockpit stores as
  `suspendedBy`. The audit log has entries only for authenticated requests. Without an entry nobody
  is named, and an activation carries the time of the run.
- The set of the run before lives in memory. The first run after a start reports every suspended
  instance again, which the cockpit takes as a repetition. It also reads the audit log of the last
  day for resumptions, so a resumption during a restart is found where the cluster has an audit log.
- Every node of the application runs the check. The platform offers no leader election to an
  extension, and the cockpit takes a repeated report as a repetition.
- A failed search leaves the set of the run before as it was. The next run finds the same changes.
- Lines 8.8 and 8.9 ask nothing. Their clusters cannot suspend. `Camunda8SuspendedInstances` is the
  part per release line.

**What was measured.** Against `camunda/camunda:8.10.7` with H2 on 2026-11-02, 1,200 instances of
two processes, 600 of them suspended:

|                                Search                                |                Result                |
|----------------------------------------------------------------------|--------------------------------------|
| `state=SUSPENDED`, `processDefinitionId in` two ids, page of 1,000   | 600 instances, one page, 99 ms       |
| The same with a page of 100                                          | seven pages, 634 ms                  |
| A page of 10,000                                                     | accepted, 94 ms                      |
| `processInstanceKey in` 1, 10, 100, 500, 1,000 keys                  | all found, 81 to 125 ms              |
| `processInstanceKey in` 10,000 keys (1,200 of them real)             | accepted, 210 ms                     |
| User tasks by `processInstanceKey in` 500 keys, state `CREATED`      | 500 tasks, 126 ms                    |
| Variables by `processInstanceKey in` 500 keys and `name in` one name | 500 values, 104 ms                   |
| Audit log `SUSPEND`/`RESUME`, `processDefinitionId in`, since a mark | 610 entries, one page, 172 ms        |
| Audit log by `processInstanceKey in` 10 keys                         | 20 entries, 83 ms                    |
| Cancelling a suspended instance                                      | accepted, the instance is TERMINATED |

The audit log was searched with basic authentication. Its entries named the user (`USER/demo`).
A list of keys is still cut into parts of 1,000, so one request stays small on every storage.

**What was not done.** A suspension is not reported at once when the cluster refuses to complete a
task of a suspended instance. The platform recognises that refusal (`WorkflowSuspendedException`),
but it throws it to the application, which made the call. No hook of the extension SPI tells an
extension about it, and the listener jobs of this extension never meet the refusal. The audit log
is not the only signal either, although it is cheap: a cluster with an unprotected API writes no
entry.
