### A suspension the Camunda 8 adapter runs into is reported at once

Proposed by story 2074. It adds to decision 36. The rule for the call itself is the platform's
decision in `adapter-platform-integration/DECISIONS.pending/2074.md`: the one call to an extension
while workflows run is synchronous, isolated and has no outbox.

**What holds.**

- `Camunda8CockpitWiring#workflowFoundSuspended` hands the process instance key, the module and the
  aggregate id to `Camunda8SuspensionCheck#foundSuspended`, and returns at once. The work runs on the
  thread of the suspension check, never on the caller's.
- An instance the check knows already is skipped without a request. That is the debounce: a waiting
  outbox entry is reported every 30 seconds.
- Otherwise one search reads the instance. If it is no longer `SUSPENDED`, nothing is reported. If it
  is, it is reported as a run would: the workflow and its open user tasks, the person from the audit
  log, and the event id `suspended-<key>-<suspendedDate millis>`. So the cockpit takes the report of a
  later run as a repetition. The aggregate id of the event saves the search for its variable.
- The instance is then put into the set of the run before, so the next run reports nothing new. Before
  the first run there is no set yet. That run reports every suspended instance anyway, and the
  restart rules of decision 36 stay as they are.
- With `suspension-check-interval: 0` the event is still reported. A resumption is then never seen.

**Tests.** `Camunda8SuspensionCheckTest#anInstanceTheAdapterFoundIsReportedAtOnce`,
`#aKnownInstanceIsNotReportedAgain`, `#theNextRunKnowsTheInstance`,
`#anInstanceWhichRunsAgainIsNotReported`, `#theReportRunsOnTheThreadOfTheCheck`.

**Where it is cited.** javadoc of `Camunda8SuspensionCheck` and `Camunda8CockpitWiring`, the README
section "A suspended workflow", `GAPS.md` gap 6.
